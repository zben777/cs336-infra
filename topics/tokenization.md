# 专题 · 分词（Tokenization）

> 跨 L1（BPE 原理）与 L10（分词对推理成本的影响）。核心是一条自己推导出来的链：**目的 → 纯字节可行但太贵 → BPE 在达成目的的前提下压短序列**。

## 一、分词的目的是什么

**目的：让模型能算文字。** 模型只认整数、不认字符，所以必须把文本翻译成整数 ID，再经 embedding 矩阵查表变成向量。分词器就是这本「密码本」。

**"更少的 token"不是目的，是副产品 / 优化指标。** 因果别搞反：

| 层次 | 问题 | 回答 |
| :--- | :--- | :--- |
| 目的 | 能不能处理 | 模型只认数字，文字必须翻译 —— 分词存在的根本原因 |
| 优化 | 贵不贵 | 更少 token → 序列短 → 省注意力、省计费 —— 做得好不好的尺子 |

哪怕 token 一点没少（英文句子两代分词器都是 19 vs 18），分词照样必须做，因为模型根本不认字。

## 二、查字典：机制本身

```
人类文字 "人工智能"
   ↓ 分词器查词表（BPE 合并规则）
token ID 序列  [24912, ...]     ← o200k 下 2 个整数
   ↓ embedding 矩阵查表（20 万行，每行对应一个 token ID）
向量  →  模型真正计算的东西
```

- **往返无损**：`decode(encode(s))` 必须还原原文，否则是 bug
- **词表** = 一本字典，10 万～20 万条「字符串片段 ↔ 整数 ID」的对应
- 字节是翻译前的原料，token ID 是翻译后的产物——**两者是不同的账**

## 三、纯字节方案：目的能达到，但代价爆炸

1 字节 → 1 token，词表只有 256 个。任何文本拆成 UTF-8 字节流即可编码，**永不 UNK**（这是 BPE 都没有的好处，也是 byte-level 成为所有前沿分词器底座的原因）。

但代价来自注意力的**平方关系**。实测同一句话（78 字节 / 26 字）：「人工智能正在改变世界，大模型推理需要优化显存和吞吐。」

| | 纯字节方案 | BPE / o200k |
| :--- | :--- | :--- |
| 序列长度 | 78 | 17 |
| 序列长度比 | 4.6× | 1× |
| 注意力元素 n² | 78² = 6084 | 17² = 289 |
| 注意力计算量 | **21.1×** | 1× |
| KV Cache 长度 | 4.6× | 1× |

**BPE 的本质**：在"能达到目的"的前提下把序列砍短。词表从 256 涨到 20 万，换来这几倍压缩——注意力和 KV Cache 跟着省（后者直接对应 vLLM-TQ 那条线）。

## 四、BPE 怎么造词表：手算一遍

语料：`low×5, lower×2, newest×1, widest×1`，`</w>` 是词尾边界。每轮统计最高频相邻对，合并成一个新 token：

```
起点  l o w </w> ×5   l o w e r </w> ×2   n e w e s t </w>   w i d e s t </w>

第1轮  l + o      (7次) → lo      序列: lo w </w> ×5 ...
第2轮  lo + w     (7次) → low     序列: low </w> ×5 ...
第3轮  low + </w> (5次) → low</w>
第4轮  lowe       (2次) → lowe
第5轮  lowe + r   (2次) → lower
第6轮  lower+</w> (2次) → lower</w>
```

重复到词表达标（10 万+）为止。**高频组合变 1 个 token，罕见组合拆成多个**——这就是自适应计算：把算力集中到信息密集处。

**作业一的坑**：朴素 `encode` 要遍历所有合并规则（≈词表大小，10 万级），非常慢；改成只遍历「关键合并」并建索引。工程上先分块再分词。

## 五、用量实测（cl100k = GPT-4 / o200k = GPT-5）

压缩比 = 字节数 ÷ token 数，越大越省。全部为本机 `tiktoken` 实测：

| 文本 | 字节 | cl100k token（压缩比） | o200k token（压缩比） |
| :--- | ---: | ---: | ---: |
| 中文句子（26 字） | 78 | 29（2.69） | **17（4.59）** |
| 短中文词（11 字） | 33 | 12（2.75） | **7（4.71）** |
| 英文句子 | 139 | 19（7.32） | 18（7.72） |
| 代码 | 85 | 26（3.27） | 27（3.15） |
| 数字与 URL | 55 | 28（1.96） | 28（1.96） |

**为什么中文差 1.7 倍、英文几乎不变？** 看真实切片：

- `"人工智能"` → cl100k 切成 `['人','工',<半个字>,...,'能']`（5 个，汉字被拆成字节）；o200k 切成 `['人工','智能']`（2 个整词）
- 词表大了之后中文整词进词表；英文本来就能压到 7+，提升空间小
- **数字和 URL 最费 token**——每个数字、符号几乎单独一个 token

**直接影响**：同样一段中文，GPT-4 计费 token 是 GPT-5 的 1.7 倍；序列减半 → 注意力 O(n²) 省 4 倍 → KV Cache 也减半。

## 六、前沿模型用什么

**绝对主流是 byte-level BPE（BBPE）**：GPT-4o / GPT-5（`o200k_base`）、Llama 3、Qwen、DeepSeek、Claude、Mistral、GLM。共同底座是 256 字节兜底，任意字符都能分词、不出现 UNK。

要点区分三个概念：

- **BPE** 是算法：自底向上合并最高频相邻对
- **byte-level** 是字母表选择：从 256 字节而非 15 万 Unicode 码点起步
- **SentencePiece** 是框架不是算法：内部可跑 BPE 或 Unigram，把空格当普通符号（`▁`），对中日韩更友好

**例外在 Google 系**：T5 / mBART / XLM-R 用 Unigram（自顶向下剪枝），Gemini / Gemma 走 SentencePiece。Unigram 概率性分词、速度稍慢；低 TTFT 场景纯 BPE 更受青睐。WordPiece（BERT 系）是编码器时代产物，已不在前沿生成模型主流。

> 诚实说明：GPT-5 / Claude / Gemini 等闭源模型的分词器细节未全部官方公开，网上部分具体数字（词表大小、某版本用哪种算法）在不同来源间有冲突。以上为交叉验证过的定性结论。

## 我的增量

- **面试讲法**：被问"分词是干嘛的" → 先答"把文字翻译成模型能算的 ID 和向量"（目的），再说"用 byte-level 保证无 UNK、用 BPE 压短序列省注意力和 KV Cache"（优化）。别把压缩比当目的。
- **项目关联**：分词是进 GPU 前唯一能免费砍掉的计算量——序列长度直接决定注意力和 KV Cache 大小，和 vLLM-TQ 的 4-bit KV Cache 是不同层面的优化（一个在进模型前砍长度，一个在生成后省显存）。
- **待验证**：在本地 tokenizer 上画压缩比随词表大小的变化曲线；对比 o200k 与中文优化词表（Qwen）在同一批中文语料上的 token 成本。
